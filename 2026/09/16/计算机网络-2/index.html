应用层概述、Web与HTTP

学习目标

应用层概述

主机上运行着许多程序，程序之间需要交互，对于同一台主机的程序之间，通过进程间通信完成交互（锁、信号量、管道），由操作系统负责；不同主机上的程序之间，则通过网络应用层完成交互，由计算机网络负责。应用层运行在端系统(host)的各类软件中，负责与网络进行通信（提供各类网络服务，屏蔽底层网络细节）

Eg
Web服务器软件 VS Web浏览器软件
只需开发网络应用层的处理模块（HTTP消息处理）

应用层与下层网络（传输层）接口

应用程序在端系统上以进程的形式呈现（见《操作系统》课程），进程利用socket（套接字）发送/接受消息
通过传输层
Socket类似一扇门

  • 从门中向外发送消息
  • 从其他进程收到的消息堆积在门口等待接收

网络应用期望的服务

可靠传输

  • 聊天工具、支付要求传输数据100%到达
  • 有些应用（如语音对话）可以容忍一定数据丢失

高吞吐

  • 有些应用（如视频播放）有最低带宽要求，以保证服务质量
  • 其他应用根据实际分配得到的带宽进行传输

低时延

  • 有些应用（如在线游戏，电话会议）对延迟极端敏感

安全

  • 数据加密、数据完整性

实际传输层提供的服务

传输层提供2类服务

TCP服务

  • 面向连接：传输前建立连接
  • 可靠传输：丢包重传
  • 有序传输
  • 流量控制：防止接收方过载
  • 拥塞控制：防止网络核心过载
  • 无法保证：延迟, 吞吐量, 安全

UDP 服务

  • 无连接
  • 不可靠传输：可能丢包，丢包也无法回复
  • 无法保证：可靠性、顺序、流量控制、拥塞控制、延迟、吞吐量、安全

思考：为什么还会有UDP
简单、性能比TCP好、有些应用可以采用。更重要的是，某些情况下，有些应用宁可丢一些数据，也不希望为了重传而产生额外延迟。譬如在线通话这类，中间丢失少量数据对整体的通话质量影响不大

网络应用层的好处

屏蔽底层细节

  • 屏蔽传输层：TCP与UDP的差异
  • 进一步屏蔽更低层次：无需为下层网络设备编写代码
  • 无需考虑端系统上的网卡设备与其他网络软件
  • 无需考虑网络核心中的路由器交换机
  • 这些网络设备通常也不在乎应用层逻辑
    抽象
  • 许多网络应用有相同的通信模式
  • 网络应用层封装这些共同模式
    提供额外的功能
  • 安全性、服务质量

总而言之：网络应用层极大简化了网络应用开发，使得互联网可以快速发展

应用程序的组织架构

客户/服务器（C/S, Client/Server）方式

客户就是在一次网络服务中，请求服务的那一方实体，而服务器就是响应服务的实体。应用层下强调的实体就是应用进程（不是电脑本身）。应用层的许多协议是基于C/S方式，例如，在移动互联网环境下，每个应用APP都是一个客户端。客户(client)和服务器(server)是指通信中所涉及的2个应用进程：

  • 一个客户端可以向多个服务器发起通信
  • 一个服务器也可以响应多个客户端
客户端程序：主动发起通话 服务器程序：等待被连接
可以临时接入 必须始终在线
可以使用动态IP地址和端口 必须有固定IP地址与端口
互相不通信 可以扩展多个实体共同完成任务
C/S方式的分类

根据是否建立连接：

  • 可以是面向连接的（TCP），也可以是无连接的（UDP）

根据服务器进程的实现方式

  • 服务器采用循环方式(iterative mode)
    一次只运行一个服务进程
    当有多个客户进程请求服务时，服务进程就按请求的先后顺序依次做出响应 (阻塞)

  • 服务器采用并发方式(concurrent mode)
    可以同时运行多个服务进程
    每一个服务进程都对某个特定的客户进程做出响应 (非阻塞)
    总共4种组合

循环方式

一个服务进程在同一时间只能向一个客户进程提供服务。(顺序服务)

  • 服务进程收到客户进程的请求后，对其他客户进程发来的请求则暂时不予理睬，这些请求都在服务端的队列中排队等候服务进程的处理。当服务进程处理完毕一个请求时，就从队列中读取来自下一个客户进程的请求，然后继续处理

无论面向连接的TCP，还是无连接的UDP，都可以采用循环方式

面向连接的循环方式：

面向连接的循环方式中应用TCP协议，在服务端采用了两个套接字，一个服务套接字和一个连接套接字，其中服务套接字负责监听熟知端口（即服务器进程工作的端口）、接受客户端发来的服务请求，然后根据连接请求创建对应的连接套接字。

详细讲解一下这里的TCP套接字工作。

首先需要明确IP地址 ≠ 端口 ≠ Socket ≠ TCP连接，这是四个不同层次的东西，Socket也不是简单的“IP+端口”的组合，而是操作系统给应用程序提供的一个通信端口。即使两个Socket采用了相同的端口，也仍然可以是两个不同的Socket。

当TCP服务套接字收到服务请求的时候，实际上同时收到了一个包含源 IP、源端口、目的 IP、目的端口相关信息的四元组，根据这些信息，TCP服务进程可以针对对应四元组开一个连接套接字（仍然在服务器的此端口上），然后通过这个连接套接字完成本次服务的任务。此机制下同一端口下可以开多个连接套接字，通过特定的源IP、源端口标记不同的Socket。不难想到并发服务的机制，也就是服务套接字收到请求后，服务进程就可以创建对应的从属服务进程，并创建对应的连接套接字，这样就可以并行处理多个服务请求：

  • 面向连接的TCP服务进程通常都工作在并发服务方式（尽管也可以使用循环方式）
  • 服务进程在同一时间可同时向多个客户进程提供服务(并发服务)
  • 在TCP服务进程与多个客户进程之间建立多条TCP连接，每条TCP连接在其数据传送完毕后释放

无连接的循环方式：

应用UDP协议，在无连接的服务中，服务器通常只有一个UDP Socket来监听客户的请求，所以只能采取循环服务方式，后续请求等排队等待，无法像面向连接的服务那样被多个从属服务进程同时访问。UDP无需像TCP那样提供一个确保联系的连接套接字，他只负责单次请求的接受以及回复——于是无需创建多个进程接口套接字，也就无法并行服务了。注意，UDP不是不能并行处理，而是循环处理才能发挥到它本身的优点

对等（P2P，Peer to Peer）方式

对等方式是指两个进程在通信时并不区分服务的请求方和服务的提供方。只要两个主机都运行P2P软件，它们就可以进行平等、对等的通信，双方都可以下载对方存储在硬盘中的共享文档，如果权限允许的话。应用中，每个节点既可以是服务器，也可以是客户端。

应用

  • 音频/视频应用推动了P2P对等通信方式的发展
  • 音频/视频流量已占主要比例

P2P方式从本质上看仍然是使用了C/S方式，但强调的是通信过程中的对等，这时每一个P2P进程既是客户同时也是服务器。可做区分，这里C/S 是某一次通信中的角色；P2P 是整个系统组织方式

特征

不需要总是在线

  • 虽然每个程序也扮演服务器角色，但与“客户端-服务器”中不同，不需要始终在线
  • 实体可以随时进入与退出
  • 可以动态改变IP地址
  • 需要额外的管理开销

任意两个实体之间可以直接通信

  • C/S方式中，客户端之间的交互往往需要服务器的中转

易于扩展

  • 每个结点都贡献自己的计算资源
  • 也消耗一部分资源

HTTP：访问Web资源的协议

超文本传输协议HTTP（ HyperText Transfer Protocol）在传输层通常使用TCP协议，缺省使用TCP的80端口
HTTP为无状态协议，服务器端不保留之前请求的状态信息。状态指应用是否还保留用户访问记录信息。某个用户二次访问服务器后，HTTP协议不会因为之前访问过而记住这个用户，而是只知道这是有一个请求

  • 无状态协议：效率低、但简单
  • 有状态协议：维护状态相对复杂，需要维护历史信息，在客户端或服务器出现故障时，需要保持状态的一致性等

HTTP标准

  • HTTP/1.0: RFC 1945（1996年）：非持久连接

此时每次请求web对象，TCP都要三次握手（连接的建立、数据传输、连接终止）建立连接，并且存在慢启动，使得执行速度很慢

Eg
一个Web资源包含两张图片，就需要三次完整的连接过程，分别获得index.html、图片资源1、图片资源2

  • HTTP/1.1: RFC 2616（1999年）：持久连接

在相同的TCP连接上，服务器接收请求、响应；再接收请求、响应；响应后保持连接。相当于不再重复建立连接和连接终止，只存在数据请求+数据传输这一次“握手”。
HTTP/1.1-pipeline 支持流水线机制

  • 需要按序响应每一次数据请求（可能存在有些资源大，有些资源小，按需加载资源如果先加载大资源，会影响体验等）
    经历较少的慢启动过程，减少往返时间

  • 降低响应时间

  • HTTP/2: RFC 7540（2015年）、RFC 8740（2020年）：多路复用

HTTP 2可以允许请求/响应交错，还可以自定义优先级，不再要求整个请求严格排队，多个资源可以并行加载。同时服务器可以主动推送消息，确认客户端存活，预测资源请求

HTTP请求报文结构

请求报文由三个部分组成，即开始行、首部行和实体主体
在请求报文中，开始行又称请求行

方法

方法是对所请求的对象进行的操作，实际上也就是一些命令。请求报文的类型是由它所采用的方法决定的

方法或操作 含义
GET（最常用） 请求读取由 URL所标志的信息
POST（最常用） 向URL提交数据（例如，参数、注释）

POST方法也可以用于请求URL资源
不同之处

  • GET方法参数在请求行URL。通常浏览器或服务器对URL长度有限制，因此参数长度有限
  • POST方法的参数在实体主体中，参数长度没有限制

一些详细解释：

POST 最核心的语义可以理解为：

把数据提交给某个目标资源，由服务器根据该资源自身的语义对数据进行处理。POST 的 URI 通常表示请求的处理目标，而不一定是客户端希望最终创建的具体资源。以 POST /users 为例，客户端是向 /users 这个资源提交数据，服务器可以据此创建 /users/123 等具体资源。

POST 的 URI 通常表示“处理这个请求的资源”，而不是客户端想创建的那个具体资源。也就是POST往往代表任务背景状态，要求服务器在这个状态下完成请求。

PUT 的核心语义则是：

客户端明确指定目标资源的 URI，并向该 URI 提交该资源的新表示。若该资源不存在，可以创建；若已经存在，则将其替换为请求所表示的状态。因此，PUT 的核心不是“定义一个新资源”，而是客户端明确指定“我要设置的是哪个资源”。

也就是定义一个资源状态

特性 POST PUT
基本语义 向目标资源提交数据进行处理 创建/替换指定 URI 的资源
URI 通常由谁确定 服务器决定具体新资源 URI 客户端指定目标 URI
是否幂等 通常非幂等 幂等
可以创建资源吗 可以 可以
可以修改资源吗 可以 可以
典型用途 创建资源、提交表单、执行操作 创建/整体替换指定资源
重复发送 可能产生多个效果 最终资源状态应相同

有时URL会带一些参数，参数以“?”开始，每个参数的形式为“[name]=[value]”，参数之间以“&”隔开

HTTP响应报文结构

与请求报文类似，由三个部分组成，即开始行、首部行和实体主体
在响应报文中，开始行又称状态行

状态码

状态码都是三位数字

  • 1xx 表示通知信息的，如请求收到了或正在进行处理。
  • 2xx 表示成功，如接受或知道了。
  • 3xx 表示重定向，表示要完成请求还必须采取进一步的行动。
  • 4xx 表示客户的差错，如请求中有错误的语法或不能完成。
  • 5xx 表示服务器的差错，如服务器失效无法完成请求。

典型的状态码

  • 200 OK
    请求成功，被请求的对象包含在该响应的数据部分
  • 301 Moved Permanently
    请求的对象被移走，新的位置在响应中通过Location: 给出
  • 400 Bad Request
    服务器不能解释请求报文
  • 404 Not Found
    服务器中找不到请求的文档
  • 505 HTTP Version Not Supported
    服务器不支持相应的HTTP版本
Web缓存技术与Web代理

浏览器缓存

  • 在浏览器主机保存用户访问过的服务器Web页副本
  • 再次访问该页，不必从服务器再次传输，提高访问效率
  • 打开网页，先检查Web浏览器上的缓存，然后发起条件GET，询问Web服务器是否有资源发生更改，服务器再决定是回传整个Web资源还是部分内容

浏览器缓存存在缓解HTTP无状态协议的无记忆问题，但主要是来cookie解决这个无状态问题

代理服务器缓存

  • ISP安装Web代理缓存服务器，保存ISP客户访问过的服务器Web页副本
  • 副本可以供ISP的所有客户访问，提高访问服务器的Web页效率
